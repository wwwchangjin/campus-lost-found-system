## 二、端到端业务流程（五条主线）

**主线一：寻物（失主视角）**
失主发现遗失 → `UC-01 发布寻物` → `UC-02 检索招领信息` → 找到候选 → `UC-03 查询暂存状态与领取指引` → `UC-09 了解归属证明方式` → `UC-18 提交在线认领申请`（线下申请直接进入 UC-10）→ `UC-10 审核归属证据` →（`UC-19 补充证明` / `UC-20 查看进度`）→ `UC-11 确认交付` → `UC-16 标记"已找回"`。

**主线二：招领（拾得者→工作人员→失主）**
拾得者捡到物品 → `UC-04 发布拾物信息`（公开普通描述）→ `UC-05 查询物品移交渠道` → 实物移交暂存点 → `UC-07 登记与编号暂存物品` → `UC-06 查看移交接收结果` →（工作人员侧：`UC-08 按编号和类别查找库存`、`UC-21 查询经手记录`）→ 失主经 UC-02/UC-03 发现并认领 → `UC-10 审核` → `UC-11 交付`。

**主线三：信息维护（失主）**
`UC-16 更新寻物信息及处理状态`——修改描述、标记"已找回"，避免过时信息误导他人；他人可经 `UC-17 向失主反馈物品线索` 协助寻找；`UC-22 处理虚假或不合规信息`、`UC-14 多人认领争议复核`、`UC-15 到期未领处置` 构成管理侧治理闭环，分别在信息可信、交付争议与物品去向上阻断风险。

**主线四：通知与外部集成**
`UC-13 关键节点通知` 提供站内通知兜底；`UC-25 经授权的外部通知渠道` 在选定第三方服务后承担外部触达。二者均不得以「本地模拟」冒充已完成集成。

**主线五：非功能保障（横切主线一～四）**
`UC-12 保护敏感信息及核验材料`、`UC-23 角色权限隔离`、`UC-24 检索响应与易用性` 横切所有业务用例，在各自异常流程中以越权、脱敏、响应时延等形式被引用，并在 SRS 中单列指标与测量方法。

## 三、用例场景详述

### UC-01 发布寻物信息

| 字段 | 内容 |
|---|---|
| 用例编号 | UC-01 |
| 用例名称 | 发布寻物信息 |
| 对应用户故事 | US-01 |
| 主参与者 | 失主（遗失物品的学生/教职工） |
| 次参与者 | — |
| 触发条件 | 失主发现物品遗失，希望发布寻物信息让线索持有者能反馈 |
| 前置条件 | 失主已登录并具有发布权限；已进入寻物信息发布页面 |
| 成功保证 | 系统新增一条"寻找中"状态的寻物记录，可被授权用户检索，发布者可在"我的发布"查看 |
| 失败保证 | 不产生任何寻物记录；用户停留在编辑页并看到明确的失败/缺失提示 |

**基本流程（正常流程）**

1. 失主选择"发布寻物信息"入口。
2. 系统展示寻物发布表单，字段包括：物品类别、遗失时间、遗失地点、物品描述（必填），以及可选的联系方式展示方式。
3. 失主填写必填字段，确认发布。
4. 系统校验字段完整性与内容合规性（不含他人证件号、联系方式等敏感内容）。
5. 系统保存寻物记录，生成唯一记录编号，初始状态置为"寻找中"。
6. 系统在允许公开的展示范围内发布该信息，并提示发布成功。

**备选流程（正常分支）**

- 3a. 失主选择"暂存草稿"：系统保存草稿且不公开，失主可稍后继续编辑后提交。

**异常流程**

- 4a. 必填字段缺失（如未填写遗失地点）：系统提示具体缺失字段，不发布不完整信息。
- 4b. 描述含不宜公开的敏感信息（身份证号、完整联系方式等）：系统提示删除或转为非公开字段后再发布。
- 4c. 失主未登录或已无发布权限：系统拒绝操作并引导登录。
- 5a. 系统保存失败（服务异常）：提示稍后重试，不产生半条记录。

**业务规则**

- 遗失地点为必填项；寻物信息初始状态为"寻找中"。
- 公开范围内不得出现身份证号、完整学号、设备密码等敏感信息。

**待确认事项**

- 失主身份验证方式（校园统一认证 or 账号注册）。
- 线索反馈渠道（联系方式是否公开、如何脱敏转达）。

**依据** 报告 §4.7（33/57 选"发布寻物信息"为优先功能）、§8.1。

### UC-02 分类检索招领信息

| 字段 | 内容 |
|---|---|
| 用例编号 | UC-02 |
| 用例名称 | 分类检索招领信息 |
| 对应用户故事 | US-02 |
| 主参与者 | 失主（或任何有检索权限的用户） |
| 次参与者 | — |
| 触发条件 | 用户想查找是否存在与遗失物品匹配的招领信息 |
| 前置条件 | 系统存在可公开检索的招领记录 |
| 成功保证 | 用户看到符合筛选条件的可公开招领记录列表 |
| 失败保证 | 无匹配时明确提示；不返回不符合条件或非公开的记录 |

**基本流程（正常流程）**

1. 用户进入招领信息检索页。
2. 用户设置筛选条件：物品类别、时间范围、地点、关键词（可组合）。
3. 用户执行查询。
4. 系统按条件过滤"可公开"的招领记录。
5. 系统展示结果列表，仅含公开字段（类别、时间范围、地点、普通外观等）。
6. 用户点击某条记录进入详情（衔接 UC-03）。

**备选流程（正常分支）**

- 3a. 用户不设条件直接查询：系统返回全部可公开招领记录，按时间倒序排列。

**异常流程**

- 4a. 无匹配记录：系统显示"暂无符合条件的招领信息"，且不返回不符合条件的记录。
- 5a. 检索接口被越权调用，试图获取非公开核验材料：系统仅返回公开字段，不返回独有标记、证件信息等（关联 US-12/US-23）。

**业务规则**

- 检索仅返回"可公开"记录与公开字段；非公开核验材料不进入检索结果。
- 空结果必须给出明确提示，不得静默无反馈。

**待确认事项**

- 具体筛选项粒度（地点到校区/楼宇/楼层？时间到日/小时？）。
- 是否支持模糊搜索与关键词匹配方式。

**依据** 报告 §3.3（36/57 认为渠道分散）、§4.4、§8.1。

### UC-03 查询暂存状态及领取指引

| 字段 | 内容 |
|---|---|
| 用例编号 | UC-03 |
| 用例名称 | 查询暂存状态及领取指引 |
| 对应用户故事 | US-03 |
| 主参与者 | 失主 |
| 次参与者 | — |
| 触发条件 | 用户打开某条招领信息详情，想确认物品是否已被暂存点实际接收、去哪领取 |
| 前置条件 | 系统存在该招领信息；其是否关联到暂存登记记录均可 |
| 成功保证 | 用户获得真实、可核实的接收状态与领取指引（或"未确认接收"提示） |
| 失败保证 | 不展示虚构的"已入库"或错误领取地点/时段 |

**基本流程（正常流程）**

1. 用户打开招领信息详情。
2. 系统查询该招领记录关联的暂存登记状态。
3. 若已确认接收：系统展示"已接收"状态、暂存点名称、领取地点、可用服务时段。
4. 用户据此决定是否前往领取或联系工作人员。

**备选流程（正常分支）**

- 2a. 招领记录尚未关联任何暂存登记：系统展示"未确认接收"状态，不显示领取地点。

**异常流程**

- 3a. 服务时段信息缺失或待核实：系统提示"服务时段待核实"，不显示可能错误的时段。
- 3b. 数据不一致（招领记录声称已接收但无对应登记）：系统按"未确认接收"展示，避免误导（关联 UC-07 的显式关联规则）。

**业务规则**

- 仅当工作人员实际确认接收后，才可展示"已接收/已入库"。
- 默认不公开具体库位；领取指引以暂存点名称、地点、服务时段为准。

**待确认事项**

- 是否公开具体库位；服务时段信息由哪个角色维护。
- 领取地点与"多暂存点"时的对应关系。

**依据** 报告 §4.5、§5.1（L02 领取受开放时间/门禁影响）、§8.1。

### UC-04 发布拾物信息

| 字段 | 内容 |
|---|---|
| 用例编号 | UC-04 |
| 用例名称 | 发布拾物信息 |
| 对应用户故事 | US-04 |
| 主参与者 | 拾得者（捡到物品的师生） |
| 次参与者 | — |
| 触发条件 | 拾得者捡到他人遗失物品，希望发布招领信息以便失主发现 |
| 前置条件 | 拾得者已登录并进入招领登记页面 |
| 成功保证 | 新增一条招领记录，公开普通描述；独有标记与敏感信息不入公开字段 |
| 失败保证 | 不产生记录或公开了不应公开的信息；给出明确失败提示 |

**基本流程（正常流程）**

1. 拾得者选择"发布拾物信息"入口。
2. 系统展示招领登记表单：物品类别、发现时间、发现地点、一般外观描述（必填）。
3. 拾得者填写必要信息并提交。
4. 系统校验字段完整性与内容合规性（执行敏感信息检查）。
5. 系统保存招领记录，生成记录编号，状态置为"待接收/寻找失主"。
6. 系统公开展示可公开的普通描述，不公开可用于冒领的独有标记。

**备选流程（正常分支）**

- 3a. 拾得者同时计划将实物移交暂存点：系统引导其查询移交渠道（对应 US-05，本批未展开）。

**异常流程**

- 4a. 提交内容含证件号码或物品独有标记：公开展示前要求删除或遮蔽，独有信息不得进入公开检索结果。
- 4b. 必填字段缺失：提示具体缺失字段，不提交。
- 4c. 系统保存失败：提示稍后重试。

**业务规则**

- 公开描述与核验材料分离：独有标记、完整证件信息只进非公开字段。
- 招领记录初始状态不得被误标为"已入库"（入库需经 UC-07 显式关联）。

**待确认事项**

- 招领信息是否需人工审核后公开（参考黄山学院"安全管理处审核"）。
- 是否允许上传照片及照片的脱敏规则。

**依据** 报告 §4.7（41/57 选"发布拾物信息"）、竞品分析 §4（公开描述与核验材料分开）。

### UC-05 查询物品移交渠道

| 字段 | 内容 |
|---|---|
| 用例编号 | UC-05 |
| 用例名称 | 查询物品移交渠道 |
| 对应用户故事 | US-05 |
| 主参与者 | 拾得者 |
| 次参与者 | 暂存点工作人员（维护暂存点信息） |
| 触发条件 | 拾得者捡到物品，希望知道可以交到哪个暂存点 |
| 前置条件 | 系统维护了暂存点及其服务信息 |
| 成功保证 | 拾得者获得经确认的暂存点名称、地点、服务时段及移交注意事项 |
| 失败保证 | 不将未经确认的地点标记为"可接收"，不展示虚构的服务时段 |

**基本流程（正常流程）**

1. 拾得者进入"移交指引"页面。
2. 系统列出已确认的暂存点，展示名称、地点、服务时段、可接收的物品范围。
3. 拾得者选择一个暂存点查看详情。
4. 系统展示该暂存点的移交注意事项（是否需预约、是否接收贵重物品等）。
5. 拾得者据此前往移交（衔接 UC-07 登记）。

**备选流程（正常分支）**

- 2a. 拾得者按位置或物品类别筛选：系统只返回符合条件的已确认暂存点。

**异常流程**

- 1a. 系统暂无经确认的暂存点及服务信息：提示"暂存点信息待核实"，不将任何地点标为正式接收点。
- 3a. 某暂存点服务时段缺失：标记"服务时段待核实"，不显示推测的时段。
- 4a. 未登录用户请求暂存点内部信息：仅返回公开指引，拒绝返回内部库位或经手人信息。

**业务规则**

- 只有经工作人员确认维护的暂存点才能标记为"可接收"。
- 服务时段以工作人员维护的数据为准，缺失时不得推测。

**待确认事项**

- 哪些岗位（图书馆/保安/便利店/班车等）是正式暂存点。
- 是否提供地图导航或距离信息。

**依据** 报告 §4.5（33/57 关注位置方便）、§5.2（各岗位接收方式不统一）。

### UC-10 审核归属证据

- 只有"通过"的请求才能进入可交付状态；"不通过/需补充"不得进入交付完成。

**待确认事项**

- 是否采用线上认领申请（关联 US-18，P2）；审核角色授权规则。
- 不同物品类型的最小有效证明规则（关联 US-09）。

**基本流程（正常流程）**

2. 获授权人员将物品标记为"争议待复核"，系统冻结交付入口。
3. 复核人员查看各申请的非公开证明材料与审核记录。
4. 复核人员作出决定（维持某申请、撤销某申请、要求补充、转线下处理）。
5. 系统记录决定、理由、操作人与时间。
6. 依决定解除冻结或终止相应申请，物品回到可处理状态。

**备选流程（正常分支）**

**异常流程**

- 4b. 复核决定未填写理由：系统不允许提交。

**业务规则**

- 争议状态下禁止交付；只有获授权角色可解除。
- 复核决定不可删除，只能追加更正记录。

**待确认事项**

**依据** 报告 §7.2、§8.5（M03 曾出现冒领）；竞品分析 §3 场景二。

**依据** 报告 §4.6（信息真实可靠评分均值 3.96）、§8.4、§8.5；竞品分析 §1.2、§2（黄山学院信息审核案例）。

### UC-23 角色权限隔离（非功能用例）

| 字段 | 内容 |
|---|---|
| 用例编号 | UC-23 |
| 用例名称 | 角色权限隔离 |
| 对应用户故事 | US-23 |
| 主参与者 | 师生（普通用户） |
| 次参与者 | 暂存点工作人员、系统管理人员 |
| 触发条件 | 任意角色访问系统页面或接口 |
| 前置条件 | 系统已配置普通用户、暂存点工作人员、系统管理人员三类角色及测试账户 |
| 成功保证 | 各角色只能完成其被授权操作，越权请求被服务端拒绝 |
| 失败保证 | 出现越权成功即视为用例失败 |

**基本流程（正常流程）**

1. 用户登录，系统加载其角色与权限。
2. 系统按权限隐藏或显示功能入口。
3. 用户发起业务操作。
4. 服务端对每次请求校验角色权限与数据范围。
5. 授权操作正常执行；未授权请求返回拒绝并记录。

**备选流程（正常分支）**

- 1a. 角色发生变更：按新角色权限生效（是否需重新登录待定）。

**异常流程**

- 3a. 普通用户直接调用内部查询或审核接口：服务端拒绝，数据不变，不返回受保护字段。
- 4a. 权限配置缺失或异常：默认按最小权限处理，拒绝敏感操作。
- 4b. 跨用户访问他人数据：系统拒绝并记录访问尝试。

**验收指标（拟议）**

- 以"角色 × 功能 × 数据"权限矩阵为测试基准，覆盖三类角色的正向授权与反向拒绝用例，全部符合预期即通过；矩阵需评审确认。

**业务规则**

- 前端隐藏不作为安全边界，必须以服务端校验为准。
- 默认最小权限；越权尝试留痕。

**待确认事项**

- 完整权限矩阵；失主/拾得者是否共用同一普通账户；工作人员与管理人员的操作边界。

**依据** 报告 §3.3、§8.4、§9.1；课程《软件工程课程设计要求（版本2）》§2.1。

### UC-24 公开信息检索响应与易用性（非功能用例）

| 字段 | 内容 |
|---|---|
| 用例编号 | UC-24 |
| 用例名称 | 公开信息检索响应与易用性 |
| 对应用户故事 | US-24 |
| 主参与者 | 失主 |
| 次参与者 | — |
| 触发条件 | 用户在常见数据量下执行检索 |
| 前置条件 | 测试环境已记录硬件、软件版本与网络条件；系统含至少 1000 条可公开测试记录 |
| 成功保证 | 绝大多数检索在规定时间内返回且结果与条件一致；无结果时提示明确 |
| 失败保证 | 超时或结果不一致均判定不通过，需定位后复测 |

**基本流程（正常流程）**

1. 准备测试数据与 100 组典型检索条件（类别/时间/地点/关键词组合）。
2. 逐组执行检索并记录服务端响应时间。
3. 核对返回结果与筛选条件是否一致。
4. 统计达标次数与平均响应时间。
5. 对无结果条件，检查是否显示明确提示。

**备选流程（正常分支）**

- 5a. 增加数据量扩展测试（如 5000 条）：记录性能变化趋势，供 SRS 阈值参考。

**异常流程**

- 3a. 检索超时或报错：系统给出明确错误提示与重试引导，不静默失败。
- 3b. 结果包含不符合条件的记录：判定不通过，记录为缺陷。
- 1a. 测试环境与正式环境不一致：结论仅对被测环境有效，需在 SRS 中注明。

**验收指标（拟议）**

- 至少 95/100 次检索的服务端响应时间不超过 3 秒，且结果与筛选条件一致。该阈值属工程拟议，需评审确认。

**业务规则**

- 阈值、测试规模与测试环境须在 SRS 中写明，不得作为已确认的用户需求表述。

**待确认事项**

- 目标设备与网络环境；正式响应时间阈值；测试数据规模。

**依据** 报告 §4.4（渠道分散）、§4.6（检索便利性均值 3.95）、§8.4。

### UC-25 接入经授权的外部通知渠道

| 字段 | 内容 |
|---|---|
| 用例编号 | UC-25 |
| 用例名称 | 接入经授权的外部通知渠道 |
| 对应用户故事 | US-25（待选型） |
| 主参与者 | 失主（订阅通知者） |
| 次参与者 | 外部消息服务（邮件/微信/短信之一） |
| 触发条件 | 认领审核结果或可领取状态发生变化 |
| 前置条件 | 项目已选定并合法配置至少一种外部消息服务；测试账户已授权接收 |
| 成功保证 | 系统调用外部服务并保存调用结果，可提供实际接收记录或服务端回执 |
| 失败保证 | 发送失败时记录失败状态，不宣称送达，不影响审核结果 |

**基本流程（正常流程）**

1. 用户在设置中启用外部通知并完成授权。
2. 系统在约定事件触发时组装脱敏消息。
3. 系统调用外部消息服务发送。
4. 系统保存调用结果（成功/失败/回执）。
5. 用户在外部渠道收到提醒，回到系统查看详情。

**备选流程（正常分支）**

- 1a. 用户关闭外部通知：仅保留站内通知（UC-13）。

**异常流程**

- 3a. 外部服务不可用或拒绝发送：记录失败状态，保留站内通知，不宣称成功送达。
- 2a. 消息内容包含非必要证明或敏感信息：系统阻止发送并要求修改模板。
- 1b. 授权凭证失效：系统标记渠道异常并提示重新授权。

**业务规则**

- 仅本地模拟发送不视为完成真实第三方集成。
- 发送前须取得用户同意；消息不含非必要认领证明与个人敏感信息。

**待确认事项**

- 邮件/微信/短信的选型；接口权限与成本；第三方不可接入时的替代方案。

**依据** 报告 §4.6、附录 A.3（微信 37/57、短信 27/57、站内 26/57）、§8.2；课程《软件工程课程设计要求（版本2）》§2.1（至少一个外部集成点）。

## 五、关键用例基线

v0.1 确定的 8 个关键用例——**UC-01 发布寻物信息、UC-02 分类检索招领信息、UC-03 查询暂存状态及领取指引、UC-04 发布拾物信息、UC-07 登记与编号暂存物品、UC-10 审核归属证据、UC-11 确认交付并阻止重复领取、UC-16 更新寻物信息及处理状态**——覆盖"寻物—招领—暂存—认领—交付"的最小业务闭环，仍作为后续关键用例建模的基准：用例图以这 8 个用例为主路径，活动图优先细化 UC-07 / UC-10 / UC-11，SRS 核心功能与测试用例优先围绕该基线展开。v0.2 新增的 17 个用例是对基线的补充与扩展（边界、异常、非功能与待验证能力），不改变上述关键用例的优先级。
